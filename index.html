Files. Chat. Video. Docs. Your agents in the room.

skhub is SKWorld's self-hosted collaboration hub: a hardened, pinned Nextcloud deployment for a sovereign fleet, where AI agents sit in chat and on calls as real teammates, not bolted-on bots. What skhub is

skhub is the deployment role (optional/skhub) inside SKStacks, SKWorld's Ansible + Docker Swarm sovereign infrastructure framework. It stands up a self-hosted Nextcloud instance, pinned by SHA-256 digest end to end, so the fleet gets its own files, chat, video calls, and office documents without handing any of it to a collaboration SaaS vendor.

Nextcloud core

Pinned nextcloud:31.0.14, backed by MariaDB 10.11.19 and Redis 8.10.2-alpine.

Security + delivery

ClamAV antivirus on uploads, a dedicated cron service, and notify_push for live, no-poll notifications.

Whiteboard + previews

Collaborative whiteboard (backend v2.0.0) and imaginary for fast image preview generation.

Collabora Online

Optional real-time collaborative document editing, Word/Excel/PowerPoint-compatible, right in the browser (26.04.5.1.1).

Talk HPB

Optional Nextcloud Talk High Performance Backend (aio-talk): Janus WebRTC signaling plus an eturnal STUN/TURN relay, for group chat and video calls.

Storage, your choice

Shared NFS by default, or point it at an external S3-compatible store, or at the fleet's own in-cluster Garage service (skstor) as a one-line shortcut.

Every image is pinned by digest, never a bare tag, and every setting comes from a per-environment vault file, never hardcoded into the playbook.

§Agents in the room, not bolted on

The point of skhub is not just that your files live somewhere you control. It is that your AI agents can work alongside you there, the same way a human teammate would: reading a shared folder, joining a conversation, picking up an @mention, sitting quietly in a room until something is actually worth saying.

That is built on hermes-nextcloud-talk, a Nextcloud Talk connector for Hermes Agent that we built and contributed upstream (merged into Hermes's own plugin catalog, PR #140445). It ships as one plugin with two independent connector modes, so you pick the integration style that fits each agent.

Two ways in: bot, or real user

ModeWhat the agent looks likeGood for
BotNo personal account. Talk's own signed Bot API (HMAC-SHA256 both directions); a moderator opts a room in with occ talk:bot:setup.A clean, no-account integration, opt-in per room, with an inbound webhook listener.
UserA genuine Nextcloud account with an app password, long-polling the Chat REST API like any human client.DMs, invites into any room, and federation across estates, with no inbound port exposed at all.

Either way, a room can run in one of three modes: mention (reply only when @mentioned, the default), watch (read every message, speak only when something is actually worth saying), or free (reply to everything, for a room dedicated to that agent). DMs always run in free mode in user mode, since there is no third party in the room to stay quiet in front of.

Federation: chat across two sovereign hubs

Talk federation lets two separate skhub instances, each with its own Talk HPB, exchange chat, reactions, and calls over the OCM protocol, group-restricted and opt-in on each side. An agent on one estate's skhub can be invited into a federated room on another estate's skhub, and the adapter auto-accepts an invitation only from an explicitly allow-listed inviter; every other invite is left pending for a human to look at, never auto-declined, never silently accepted.

Add your own agent

  1. Pick a mode. Bot (no personal account, webhook-driven) or user (a real account, app password, long-polling, DMs and federation).
  2. Create the credential. Bot: occ talk:bot:install with a generated secret. User: a dedicated Nextcloud account plus an app password from Settings → Security.
  3. Point Hermes at it. Set the matching environment variables (NEXTCLOUD_TALK_SECRET/NEXTCLOUD_TALK_BASE_URL for bot mode, or NEXTCLOUD_TALK_SERVER_URL/NEXTCLOUD_TALK_APP_PASSWORD for user mode); the plugin picks the mode automatically from which credential is set.
  4. Invite it in. Enable the bot per room, or invite the user account to a room or DM like any teammate. Done.

§Security, the boring and important kind

skhub is not "Nextcloud with defaults." It is Nextcloud run the way a sovereign fleet actually needs it run, with the rough edges found and fixed under real load, not assumed away.

  1. Sovereign by default, not by promise. File data, chat, video signaling, and documents all run on infrastructure the operator controls. There is no collaboration SaaS vendor in the data path, and the storage backend decision (NFS, external S3, or the fleet's own skstor) is made once, deliberately, up front, because Nextcloud only reads its S3 configuration on first install.
  2. CrowdSec at the edge. skhub sits behind sksec, SKWorld's shared edge layer: CrowdSec behavioral detection plus a fail-closed Traefik bouncer in front of every service, so abusive traffic is stopped before it reaches Nextcloud at all.
  3. SSO that doesn't break the clients. Nextcloud is as much an API (WebDAV, CalDAV, OCS, notify_push, Talk signaling) as it is a web app, so skhub deliberately skips a reverse-proxy SSO middleware that would break every one of those clients. Sign-in goes through Nextcloud's own user_oidc app against the fleet's Authentik instance (sksso), with automatic group mapping, a documented deprovisioning path, and a break-glass local login for recovery. Automation keeps local app passwords, never an SSO identity.
  4. Scanned uploads, tuned not to choke. Every upload is scanned by ClamAV. The stock config's database-reload memory spike was measured at +94% RSS; the tuned config removes that spike entirely while keeping the same signature database resident.
  5. Encrypted backups, at a fixed time, every night. A nightly db-backup sidecar dumps the database on a fixed wall-clock schedule (DST-correct), rather than drifting with whenever the container last restarted, so backups land at a predictable time every night and the retention window is known, not guessed.
  6. Found in production, fixed the same release cycle. A production backup job once took a full table lock for its entire multi-minute dump and queued over a hundred live Nextcloud queries behind it, stalling Talk and the web UI; the fix (--single-transaction --quick) landed with a dedicated regression test the same cycle it was found. A separate incident had Nextcloud's first install crash-looping on a busy host because the container healthcheck's grace period was shorter than the install itself was allowed to take; same pattern, same day, fixed and tested.
  7. Deploys fail loudly, not silently. A "mount drift" check refuses a deploy that would silently drop a live, still-in-use external storage mount. A config mistake shows up before it touches the running stack, not after someone notices a storage connection is gone.
  8. Nothing ships on claims alone. New skhub capability is release-gated by a dedicated lab stage in the project's own test harness (skstack06), which exercises the feature end to end against a real, disposable Nextcloud + Talk + Collabora stack: a real TURN allocation through the TLS-over-443 path, a real SMTP delivery through a lab mail server, a real bind-mount drop-and-refuse, a real federated chat message exchanged between two throwaway accounts on two separate instances.

§Calls that work off the LAN

With the optional Talk HPB enabled, Nextcloud Talk gets its own TURN/STUN relay (eturnal), so calls work from outside the local network, not just inside it. A TLS-over-443 fallback keeps calls working on networks that block the raw TURN port, and port sizing follows a simple rule of thumb: roughly 2 x N² relay ports for an N-person call outside the LAN.

§Workflows: skwrit and skflow

skhub is the fleet's "files, chat, video, docs" layer, and it is built to sit next to the rest of the stack rather than stand alone: the fleet's own matter engine (skwrit), its own workflow engine (skflow, built on Windmill), its own SSO (sksso, Authentik), and its own local-inference gateway (skgateway).

skwrit drafts -> quality gate -> independent review -> release -> published straight into skhub (Nextcloud), re-download verified a file lands in skhub (Nextcloud) -> webhook_listeners fires an event -> dedicated webhook worker delivers it (~4s, vs. up to 5 min on cron alone) -> skflow (Windmill) picks it up and runs the workflow -> a Talk notification or a reply can be sent, or a new document written back sign-in: user -> skhub login -> user_oidc -> sksso (Authentik) <- group/account mapped automatically <-

skwrit, end to end

Drafting with quality gates, an independent review step, and a release step, publishing straight into skhub, with a re-download check that confirms the published copy matches what was sent.

Fast webhooks

A dedicated background-job worker handles webhook delivery for Nextcloud's webhook_listeners app. Without it, a webhook waits for the next 5-minute cron cycle; with it, delivery has been measured at about 4 seconds on a live instance.

skflow (Windmill)

That fast delivery is what makes skhub useful as a trigger for the fleet's workflow engine: a file landing, a chat message, or a call can kick off a workflow almost immediately instead of minutes later.

skgateway for AI

Nextcloud's built-in Assistant (chat, summarize, rewrite, translate, speech-to-text) runs against the operator's own self-hosted models through skgateway's model aliases. Image generation and cloud TTS are left disabled rather than silently falling back to a cloud default.

Release process

skhub deploys through a standard Ansible playbook (deploy_skhub-<env>.yml) run per environment, dev, staging, prod, with every setting coming from a per-environment vault file. New capability is release-gated by the skstack06 lab harness before it is considered released, an evidenced practice with real bugs caught, not an aspirational claim.
